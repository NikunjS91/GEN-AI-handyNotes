today we are going to buid a system where with each agent decision human feedback is needed.
we think of writing an email — the agent will draft the email, wait for a human review, then either rewrite or send.

in simple terms: an llm runs an autonomous task, pauses for human input at a checkpoint, applies that feedback (or not), and continues.

below i explain each code block from the notebook, block-by-block, in the same style.

block 1 — load env
- from dotenv import load_dotenv
- load_dotenv()
	- loads environment variables from a `.env` file so the llm keys/configs are available to the code.

block 2 — imports
- from langgraph.graph import StateGraph, START,END
- from pydantic import BaseModel
- from langchain_groq import ChatGroq
- from langgraph.types import interrupt,Command
- from langgraph.checkpoint.memory import InMemorySaver
- from typing import Literal
	- these import the building blocks:
		- `StateGraph`, `START`, `END`: used to build the state-machine graph for the flow.
		- `BaseModel`: pydantic base for the state schema.
		- `ChatGroq`: the groq-backed chat llm wrapper used to generate drafts.
		- `interrupt`, `Command`: `interrupt` triggers a human-in-the-loop modal; `Command` is used to pass a user response when invoking the graph.
		- `InMemorySaver`: a simple in-memory checkpointer to save state between steps.
		- `Literal`: typing helper used for conditional routing return values.

block 3 — llm client
- llm = ChatGroq(model="openai/gpt-oss-20b")
	- instantiates the groq chat model wrapper. this `llm` is used to generate and rewrite email drafts.

block 4 — state schema
- class MailState(BaseModel):
-     query :str = ""
-     draft : str = ""
-     human_feedback : str =""
-     final_response : str =""
	- defines the `MailState` pydantic model that carries data across nodes:
		- `query`: user prompt (what to write)
		- `draft`: current draft text generated by the llm
		- `human_feedback`: reviewer feedback (if any)
		- `final_response`: final confirmation/result after send/rewrite

block 5 — node functions (draft, human feedback, finalize, route)
- def DraftEmailNode(state : MailState) -> MailState:
		- if state.human_feedback present → call llm with a rewrite prompt applying feedback
		- else → call llm with the original `state.query`
		- store result in `state.draft` and return state

- def HumanFeedbackNode(state: MailState) -> MailState:
		- calls `interrupt({...})` with the `draft_email` and a `question` asking the human to approve or request rewrite
		- `interrupt` blocks/waits for human input in the LangGraph flow; the returning `feedback` is the human response
		- normalize `fb` and if user replied with an approval token (`approved`, `ok`, `yes`) we clear `human_feedback` so flow can proceed
		- otherwise we set `state.human_feedback = feedback` (so next draft node will rewrite using that feedback)

- def finalizeNode (state:MailState)->MailState:
		- if `state.human_feedback` exists, put it into `state.final_response` and return (indicates human chose a final response instead of sending)
		- else, print a success message, set `state.final_response = "Email sent Successfully"`

- def condition_route(state: MailState) -> Literal["draft","final"]:
		- returns the route name used by the graph's conditional edges
		- if `state.human_feedback` is present → return "draft" (send back to drafting)
		- else → return "final" (proceed to finalize/send)

	- together these nodes implement the loop: generate draft → interrupt for feedback → if feedback ask rewrite → repeat until approved → finalize/send.

block 6 — graph construction
- graph_builder = StateGraph(MailState)
- graph_builder.add_node("draft", DraftEmailNode)
- graph_builder.add_node("human_fb", HumanFeedbackNode)
- graph_builder.add_node("final", finalizeNode)
- graph_builder.add_edge(START,"draft")
- graph_builder.add_edge("draft","human_fb")
- graph_builder.add_conditional_edges("human_fb",condition_route)
- graph_builder.add_edge("final",END)
- graph=graph_builder.compile(checkpointer=InMemorySaver())
	- build a `StateGraph` typed with `MailState`, add the named nodes and edges.
	- `add_conditional_edges` uses `condition_route` to decide whether `human_fb` routes back to `draft` or to `final`.
	- `.compile(checkpointer=InMemorySaver())` produces an executable `graph` with an in-memory checkpointer so state persists between `invoke` calls.

block 7 — visualize graph
- from IPython.display import Image
- Image(graph.get_graph().draw_mermaid_png())
	- draws the mermaid diagram of the graph so you can see the flow visually in the notebook.

block 8 — invocation config
- config = {"configurable": {"thread_id":"1"}}
	- a small config object passed when invoking the graph. here `thread_id` can be used to scope/checkpoint separate runs (so the checkpointer keys don't collide).

block 9 — initial invoke (start the flow)
- res = graph.invoke({"query":"i want to send email for medical leave to my hr, dates will be 10th august to  15th august 2026, so creata a simple mail"},config=config )
	- starts the state-machine at `START` with an initial input dict. the graph runs the `draft` node first and returns a `res` mapping containing node states/results (like `res["draft"]`).
	- because of the `human_fb` node next, execution will call `interrupt` and wait for human input (in interactive runtimes).

block 10 — inspect draft
- print(res["draft"]) 
	- shows the initial generated draft text returned from the `DraftEmailNode`.

block 11 — send human feedback / resume with changes
- res = graph.invoke(Command(resume="i want to change dates, and new dates are 7july to 21 july, and i want to remove the place holders and just say thank you"),config=config)
	- uses `Command(resume=...)` to provide the human response back into the interrupted node.
	- this simulates the user replying to the `interrupt` prompt: the graph picks the resume text up in `HumanFeedbackNode`, sets `state.human_feedback`, and the conditional route sends it back to `draft` so `DraftEmailNode` will rewrite using the new feedback.

block 12 — inspect updated draft
- print(res["draft"]) 
	- prints the rewritten draft after applying the human feedback you passed in the `Command(resume=...)`.

block 13 — final approval / resume yes
- res = graph.invoke(Command(resume="yes"),config=config)
	- send a final approval using `Command(resume="yes")`. the `HumanFeedbackNode` sees the approval, clears `human_feedback`, condition_route will now return "final", and the graph proceeds to `final` where the email is "sent" (or final_response set).

notes / tips:
- `interrupt` is the key primitive for human-in-the-loop: in interactive environments it suspends execution and surfaces a UI for human input; programmatically you respond using `Command(resume=...)` on subsequent `graph.invoke` calls.
- `InMemorySaver` keeps everything in memory; for durable runs use a persistent checkpointer.
- prompts in `DraftEmailNode` are simplistic; you can make them more structured (system/instructions) to get better rewrites.
